# Durable & Reusable Learnings

## Operator Preferences
- **Model-Agnostic Adaptation**: The operator swaps between different models frequently to manage and optimize costs. System configurations, boundaries, and logic must be robust across diverse model architectures rather than overly tailored to a single option.
- **Terse Output Formatting**: Output tokens are often overly descriptive and should be far more terse. Future developments must prioritize output format efficiency, specifically starting with prefix reduction in autoresearch and progressive disclosure improvements.
- **Focus on Response Format**: The core goal is using autoresearch to improve progressive disclosure response format efficiency. Keep compression levels as-is and target other vectors for output verbosity.
- **Flexibility and Token Efficiency**: Keep a strong balance between context flexibility and token efficiency, especially for longer, more complex dynamic workflows in pi.

- **Sole maintainer (armchairfuturist-code)**: Operator is the only maintainer of github.com/armchairfuturist-code/*. For pi-harness-config: **remote `origin/master` is source of truth** — always `git fetch` before local work; when shipping, **push directly to master** (no long-lived PR theater unless asked). Local checkout can lag; never treat a dirty local tree as canonical over remote.
- **README audience**: Prefer clear operator-facing prose (goal, CE-lite why, why no MCP/web always-on, extensions table, model-agnostic). Keep lab detail in `research/` and `docs/`.

## Confirmed Gotchas & Facts
- **Context Pruning Explosion**: Entering every-turn mode with `pi-context-prune` was a critical failure. It exploded requests (from 4-5 up to 12-27 per loop) and increased total token consumption by 6x; thus, rapid reversion is required for this mode.
- **Schema Optimization via Truncation**: Live optimal is `aggressiveMaxDescChars=5` in `~/.pi/tscg.json` (Campaign 1 2026-08-03: median ~51k → ~29k, ~-43% vs prior). Prior `=30` result (~-22%, ~14.7k tokens/req) is superseded — do not revert to 30.
- **Model Destabilization via Configuration**: Custom adjustments to lean-ctx footers (`LEAN_CTX_SAVINGS_FOOTER` and `LEAN_CTX_AGGRESSIVENESS`) had negligible utility (~30 tokens saved) but heavily destabilized model behavior.
- **Tool Disablement for Context Efficacy**: Disabling high-overhead but unnecessary tools globally via `pi-lean-ctx` (`disableTools`: `ctx_doctor`, `ctx_insight`, `ctx_stats`, `ctx_upgrade`, `ctx_purge`) saves ~93 tokens on probe, yielding around ~1.5% per-request efficiency gains with zero downside.
- **MCP Bridge — enableMcp:false is LOAD-BEARING (measured 2026-07-29)**: the kernel's `enableMcp: false` is deliberate, not a bug. With the bridge ON (`true`), lean-ctx performs intent-based tool-surface expansion: trivial prompts send 22 tools (~4,005 tok) but file/agentic prompts expand to 78 tools (~13,590 tok per request, every request). With the bridge OFF, the surface stays a static lean 22 tools (~4,000 tok) even for real file tasks — the 4,007-token floor depends on this. Measured A/B through the systima proxy, same task/prompt/model: bridge-on 13,591 vs bridge-off 3,997. Cost of bridge-off: ctx_edit loses cache-coherence — fall back to Pi's native edit tool immediately when the bridge is not connected (original gotcha, still in force). Do NOT flip enableMcp to true; if the re-read caching benefit is ever wanted, measure the task-prompt payload first.
